# 周报格式规范

本参考用于补充 `SKILL.md` 中的周报正文提炼、过滤与合并细节（日期范围标题、`下周计划` 区块与文件存储规则以 `SKILL.md` 为准）。

## 输入来源

- **Git 提交**：指定时间范围内的 commit 记录（由 `src/git_analyzer.py` 或等价 `git log` 合同提取）
- **文字或截图补充**：用户口述或给出的非代码工作、commit 截图

## 正文格式

采用按项目分组的两级缩进列表结构：项目名顶格占一行，主条目使用两空格缩进，补充细节使用四空格缩进，以便与 `src/storage.py` 的合并解析和排版保持一致。

```text
项目名称
  - 主要工作点（一个具体结果，保留关键术语）
    - 补充说明（可选）
      - 更详细的补充（可选）

其他
  - 不属于特定项目的工作内容
```

## 总结与过滤原则

### 编写原则

1. **事实导向**：只总结有提交或用户描述支撑的工作；Git 提交不能独自证明已上线、已验收或业务收益。
2. **简洁精炼**：每点表达一个具体结果，不为凑字数截断术语或删掉关键行为。
3. **重点突出**：过滤琐碎修改，保留对交付结果有信息量的改动。
4. **按项目分组**：相同项目的工作归类在一起，多个项目可按工作量或重要性排序；非特定项目工作归入 `其他`。
5. **层级清晰**：用缩进表示主从关系；工作较少的周次如实记录，不刻意扩充。

### 过滤规则

以下类型的提交通常不单独列出，以免掩盖核心工作（若涉及大规模重构或重大依赖升级，可按实际影响单列）：

- 纯格式化/代码风格调整（`format`、`lint`、`style:`）
- 简单的 typo 修复（`fix typo`、`typo`）与 `update readme/changelog`
- 依赖版本小幅更新
- `wip` 提交与 Merge commit
- 重复性的相似提交（合并为一条）

### 合并规则

- 相关联的多个小改动合并为一个主题
- 同一功能的多次迭代合并为一条记录
- 问题排查与解决归为一条

```text
    - 异常处理优化
    - 方案合理性优化
    - 问题边界定义
  - 对话头像渲染
  - 脚本国际化检查优化

其他
  - 新版国际化方案讨论
```
