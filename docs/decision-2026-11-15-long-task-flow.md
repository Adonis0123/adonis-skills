# 长任务会话流程决策记录

> 状态：accepted（2026-11-16）

## 背景

回看了近期几个耗时最长的任务的会话记录，归纳出这些问题：

- 会话的大部分墙钟时间花在等用户和等后台任务上，模型和前台工具只占小部分。
- 一个会话里装了多组互不相关的需求，上下文多次压缩，单次请求体积很大。
- 用户的输入里有相当一部分是纠正。
- grill 里没回答的题被按推荐执行，却没说明取了哪些；有的推荐建立在猜的事实上，后面引出多次返工。
- 有的审查没经过审查 skill，直接调用审查者，绕开了 skill 自带的 3 轮上限，审查轮数远超上限。
- 多个会话共用一个检出和一套环境，互相占用。

联网核实的结论：

- 官方文档反对一个会话混装不相关任务（https://code.claude.com/docs/en/best-practices ，"a session that's collected three unrelated tasks re-reads all three on every turn of the fourth"，已抽查原文）。
- 官方建议多 agent 从 3–5 个起步（https://code.claude.com/docs/en/agent-teams ，已抽查原文）。
- 审查者用独立上下文有效；换厂商审查相对同模型新会话的增益不显著（https://arxiv.org/abs/2610.01471 ，未抽查原文）。
- 没查到「审到零发现」的收敛数据，也没查到 grill 式访谈的对照实验。

## 决策

1. 改进先瞄准少返工、少被打断，墙钟和花费排第二。
2. 出现与当前任务不相关的需求时，agent 写好 brief，在 Orca 里新开一个会话处理，不占用当前会话，不先问用户。同时最多 3 个由 agent 自开的会话，超过的记为 Pending Decision。
   - 做法：`orca worktree create` 建隔离目录，在它自带的第一个终端里用 `orca terminal send` 发启动命令 `sideby next <family> -- <读 brief 并执行>`。实测 `orca terminal create --command` 在没显示过的 worktree 里 3 次有 2 次变成后台句柄，所以不用它。
   - 不在 Orca 里时，退回独立的 headless 会话（Side Session），启动方式沿用 `agent-dispatch` 已有的 headless 写法。
3. 另开的会话各用各的 worktree，由开会话的 agent 创建并写进 brief；会话结束时自己移除，有未提交改动则保留并记一条 Pending Decision。test 环境不做部署排队，只在部署前检查有没有别人在部署。
4. 审查必须经审查 skill，不直接跑 `codex exec` 做审查；3 轮上限沿用现有值；本次个人配置选用 Codex 做审查者，skill 公开的默认顺序不变。
5. 第 3 轮仍有发现时：用户在场就停下汇报；无人值守就用 `sideby unattended defer` 记一条（剩几条发现、在哪个分支），不提交、不合并带未决发现的代码，继续做不依赖它的部分。
6. grill 里没回答的题按推荐执行，动手前列出取了哪几条推荐。推荐依赖只有用户知道的事实（人的角色、口味）时，等用户回答。
7. 涉及界面的任务，先给草图或截图确认形态再实现。
8. 这次不清理闲置 skill。把「近 30 天零调用的 skill 数」加进周报指标，连续两期不降再单独处理。口径只含主线程的调用。
9. `/writing-plans` 的「不用 git worktree」保留：单个计划内不拆 worktree，另开的会话才用，两者不冲突。

## 放弃的方案

- **用 `sideby ask --spec` 开新会话**：只读核实后，它只处理 sideby 自身的事务，不能带任意 brief 去别的仓库。
- **grill 里没答的题一律不执行**：用户否决，没答的本来就该按推荐走；问题出在没列出取了哪些，以及推荐建立在猜的事实上。
- **给审查新增轮数上限**：上限已存在，缺的是让审查经过 skill。
- **这次就标记闲置 skill 为 Retirement Candidate**：它不是会话变长的原因，官方依据也没核实到原文。
- **test 环境部署排队**：涉及共用环境，先只做部署前检查。

## 实现时的调整（2026-11-16）

- 第 2 条的启动命令：设了账号白名单时，从获准账号里选额度最多的，用 `sideby run <账号>` 启动；没有白名单才用 `sideby next <family>`。
- 第 4 条在本机用一个提醒 hook 落实（不在本仓），它只提醒、不拒绝：按命令文本判断是否审查会误判，拒绝会卡住其他正在跑的会话。
- 第 8 条的周报指标不在本仓实现。
- 实测发现：「经 skill 就有 3 轮上限」在实践中不总成立，按 `open-code-review-loop` 的命令形状也能超过上限。已查清：轮数只认调用方传入的账本文件，换一个文件就从 0 开始；接力后和无人值守时的「按推荐继续」又被当成了加轮授权。修复是把账本位置交给脚本决定。

## 未验证

- Orca 的建 worktree、发命令、移除、按 `side-` 前缀计数都实跑过（Orca 1.4.259、sideby 0.38.0）；真正启动一个 agent 会话、会话收尾时自己移除 worktree 没有跑。
- 「同时最多 3 个」靠 worktree 名的 `side-` 前缀计数，是尽力而为：没有工具能区分会话由谁开启。
- effort 档位和纠正率是否相关没有计算。

## 本记录之外、需另开任务的问题

都在 sideby 仓库：

- 子任务的失败通知被 network-hook 拦掉，会话空等。
- 用户在线时无人值守模式仍开着，提问被拦。
- 后台等待超过 10 分钟不主动汇报进度。
